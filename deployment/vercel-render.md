# GitHub, Vercel and Render

The repository contains app-specific Vercel configurations with same-origin API proxy functions, plus separate Render production/demo blueprints. Testing previews have existed; this guide does not configure or provision production resources. The Docker/Caddy setup in this folder is an alternative to this managed hosting route.

## Vercel projects

Connect the same GitHub repository twice. Set the customer project's Root Directory to `apps/web`, and the staff project's Root Directory to `apps/admin`. Enable inclusion of source files outside the root directory so npm workspaces can use the shared package and root lockfile. Use Node 22. The app-specific `vercel.json` supplies install/build/output and SPA navigation settings.

Set server-side `API_ORIGIN` on BOTH Vercel projects to the API service HTTPS origin, for example `https://material-square-api.onrender.com` (without `/api`). Leave `VITE_API_URL` unset so both browser apps use `/api` on their own origin. The proxy function forwards API requests and customer session cookies to the configured API origin. Vercel Preview deployments without an `API_ORIGIN` use the public demo API; Production still requires an explicit `API_ORIGIN`. Redeploy both projects after changing the variable.

Assign customer domain `YOUR-DOMAIN` (and redirect www as desired) and `staff.YOUR-DOMAIN` to the respective projects. The same-origin proxy keeps customer cookies on the customer website host and staff API calls on the admin host. Use the demo API origin for test deployments only.

## API and database

For production, create a Render Blueprint from root `render.yaml`; it creates paid resources. For a temporary hosted demo, choose Blueprint path `deployment/render-demo.yaml`, which uses Render Free compute and a separate Free Postgres database. Render Free Postgres expires after 30 days and has no backups, so never store client or production data there. Free API instances may sleep when idle. Demo mode only scopes demo records and staff credentials; customer sign-in still requires MSG91. Enter a private `DEMO_STAFF_PASSWORD` for a hosted demo; no shared default is committed in the cloud blueprint.

Set `CORS_ORIGINS` to the exact comma-separated customer and staff HTTPS origins. Keep database access private. The production API readiness check requires a reachable database, MSG91 server Authkey, exact HTTPS website origins, and complete S3-compatible image storage settings. Until these production settings are present, `/api/health/ready` returns 503 and Render will not mark the service healthy. The blueprint builds the API and applies migrations before starting. The demo blueprint also creates its staff account without resetting customer data.

Customer sign-in uses MSG91's OTP Widget. Add `MSG91_AUTHKEY` as a private Render API environment variable, and set `VITE_MSG91_WIDGET_ID` and `VITE_MSG91_TOKEN_AUTH` in the customer website's Vercel environment. The Authkey must never be added to Vercel or committed to the repository. Customer OTP verification remains active in demo mode; demo mode is only for staff/demo data scoping.

Product image uploads require an S3-compatible bucket. Set `AWS_REGION`, `AWS_S3_BUCKET`, `AWS_ACCESS_KEY_ID`, `AWS_SECRET_ACCESS_KEY`, and `AWS_S3_PUBLIC_URL` on the Render API. Set `AWS_S3_ENDPOINT` for providers such as R2 or MinIO; leave it blank for AWS S3. The public URL should be a CDN or read-only asset origin configured to serve the bucket's `images/` objects. Keep write credentials private and limit the bucket to public reads of catalogue images.

After production migration, create staff through the provider's private shell using `scripts/create-staff.cjs` and STAFF_PHONE/STAFF_EMAIL/STAFF_NAME/STAFF_PASSWORD environment values. Do not put secrets in Git or Vercel frontend variables. The API secret is generated by Render. The frontend needs only the server-side `API_ORIGIN` and the public MSG91 widget ID/token.

## Before client launch

Verify `/api/health/ready`, HTTPS, actual customer sign-in across two devices, account separation, staff phone/password login, follow-up persistence and the WhatsApp/email previews. Enable provider backup recovery and agree export retention. Set usage alerts, then complete the client content review. This blueprint does not buy services, configure DNS, or activate live SMS on its own.
