# GitHub, Vercel and Render

The repository now contains app-specific Vercel configurations and separate Render production/demo blueprints. No cloud resources have been created. The Docker/Caddy setup in this folder is an alternative to this managed hosting route.

## Vercel projects

Connect the same GitHub repository twice. Set the customer project's Root Directory to `apps/web`, and the staff project's Root Directory to `apps/admin`. Enable inclusion of source files outside the root directory so npm workspaces can use the shared package and root lockfile. Use Node 22. The app-specific `vercel.json` supplies install/build/output and SPA navigation settings.

Set `VITE_API_URL` on BOTH projects to `https://api.YOUR-DOMAIN/api`. This is a public API address, not a secret. A new deployment is required after changing it. The root Vercel config remains available for existing customer-only imports, but app-specific projects are preferred.

Assign customer domain `YOUR-DOMAIN` (and redirect www as desired) and `staff.YOUR-DOMAIN` to the respective projects. API, customer website and staff app must use HTTPS under the same parent domain, or a same-origin API proxy must be configured. Customer cookies use SameSite=Lax. A random vercel.app preview calling onrender.com is cross-site and will not support this cookie setup. Use a separate demo subdomain with `demo-api.YOUR-DOMAIN` for hosted account tests.

## API and database

For production, create a Render Blueprint from root `render.yaml`; it creates paid resources. For a temporary hosted demo, choose Blueprint path `deployment/render-demo.yaml`, which uses Render Free compute and a separate Free Postgres database. Render Free Postgres expires after 30 days and has no backups, so never store client or production data there. Free API instances may sleep when idle. Demo enables displayed OTP codes only for its configured test numbers. Enter a private `DEMO_STAFF_PASSWORD` for a hosted demo; no shared default is committed in the cloud blueprint.

Set `CORS_ORIGINS` to the exact comma-separated customer and staff HTTPS origins. For Vercel preview domains, proxy `/api/*` through each Vercel app to the Render API, preserving same-origin customer cookies; direct calls from `vercel.app` to `onrender.com` are cross-site. For domain-based testing, assign `api.YOUR-DOMAIN` (or a demo API subdomain) and keep all apps under the same parent domain. Keep database access private. The blueprint builds the API and applies migrations before starting. The demo blueprint also creates its staff account without resetting customer data.

The production blueprint defines `TWOFACTOR_API_KEY` as a private Render environment variable. Add the provider key there only after confirming the account is active and its SMS credit/template setup is ready. The backend sends OTPs server-to-server; the key does not belong in either Vercel frontend. Do not enable demo authentication on a production database to work around provider setup.

After production migration, create staff through the provider's private shell using `scripts/create-staff.cjs` and STAFF_PHONE/STAFF_EMAIL/STAFF_NAME/STAFF_PASSWORD environment values. Do not put secrets in Git or Vercel frontend variables. The API secret is generated by Render. The browser-facing apps only need VITE_API_URL.

## Before client launch

Verify `/api/health/ready`, HTTPS, actual customer sign-in across two devices, account separation, staff phone/password login, follow-up persistence and the WhatsApp/email previews. Enable provider backup recovery and agree export retention. Set usage alerts, then complete the client content review. This blueprint does not buy services, configure DNS, or activate live SMS on its own.
